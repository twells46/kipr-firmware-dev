# PR 12 regression check (`oscar/dma-write-bounds`)

Separate from the PR 8 investigation (`../investigation.md`). The same
Wombat rules apply: write the falsifier first, only one agent touches the
Wombat, never shut it down without asking, and log what was flashed.

PR 12 (`80ad31a`, on master `4814ab8`) changes `handle_dma()` in two ways:
- it clamps the count byte to 42;
- it skips writes to address < 3 or ≥ 153.

**Question:** does any legitimate traffic behave differently, or does any
corrupt traffic now behave worse?

**Status 2026-10-12 19:25Z** (H10 added; the rest is from 2026-10-01):
- No regression for legitimate traffic, on the host harness or on hardware.
- Two trade-offs were found (A9, A10). The firmware fix for both,
  Wombat-Firmware `6896e00`, was **pushed to PR 12 on 2026-10-12**, with
  the review comment in `pr12-comment.md`.
- The host side of A10 is twells46/libwallaby PR 3 (branch
  `spi-reject-warning`, commit `4a1e3b3` on master `cf56155`). It is the
  same change as `libwallaby-spi-rejects.patch`. Nothing is open against
  kipr/libwallaby.
- Both fixes are verified on hardware.
- H10 (libkipr smoke test) passes on the fix firmware, including a by-eye
  check of motors, servos and digital sensors.

## Attack summary

Two read-only review agents (host side, firmware side) plus the host
harness.

| # | Candidate | Verdict | Evidence |
|---|---|---|---|
| A1 | libwallaby or tools write registers 0..2 | Ruled out | No caller does. Only `set_servo_position(port ≤ −38)` reaches them: `servo_p.cpp:54` checks only `port > 3`, and 78 + 2·(−39) = 0. | A2 | Writes at or above 153, or more than 4 pairs | Ruled out | `platform.cpp:75/97/119` bound writes to ≤ 152. Counts are only 1, 2 or 4, and frames are `memset`-zeroed. |
| A3 | Register map mismatch | Ruled out | All 155 `REG_*` defines in `wallaby_spi_r4.h` and libwallaby `registers.hpp` match. |
| A4 | Firmware consumers of registers 0..2 | Ruled out | Only `init_tx_buffer` writes them, and nothing reads them (also true on PR 8). |
| A5 | Clamp off-by-one, `'S'` consumed | Ruled out | The last pair is bytes 86/87. Disassembly: `cmp #42; movcs`, `subs #3; cmp #149; bhi`. |
| A6 | Side-effect order (done bits, `adc_dirty`, `dig_dirty`) | Ruled out | All side-effect addresses are in 3..152. Harness T1/T2/T4. |
| A7 | Longer ISR | Ruled out | About +16 cycles per 4-write packet. H5 soak rate: master 4796 frames/s, PR 12 4798, fix 4809. |
| A8 | Merge with PR 8 / PR 13 | Ruled out | PR 8: `merge-tree` is clean, with no shared files. PR 13 is stacked on PR 12 and doesn't use the count byte or `aTxBuffer[0]`. |
| A9 | Corrupt count 128..169 with a **non-zero** body | **Real → fixed** | On master `stop` wraps, so n−128 pairs apply. PR 12 applied 42. T9b: PR 12 changed more registers in 96% of such frames (22.8 vs 11.7 bytes). H7 reproduced it on hardware (servo0 = 2000). |
| A10 | Corruption now silent | **Real → fixed** | Master turned an inflated count into a permanent `DMA de-synchronized`. PR 12 was silent. `debug_printf` is an empty stub (`wallaby.c:17`), so the SPI frame is the only channel the Pi can see. |

## Fixes (`6896e00` + libwallaby patch)

- **A9:** a count above 42 is known to be corrupt, so the firmware recovers
  the real count from where the zero padding starts (the last non-zero byte
  in 4..87).
  - If there's no zero pair before `'S'`, the body is as suspect as the
    count, and nothing is applied.
  - Single-bit flips of the count byte on libwallaby frames still apply
    exactly the real writes (T5, T6, H3).
  - Garbage bodies now apply nothing (T7, T9b, H7).
- **A10, firmware:** counts packets with a corrupt count or a skipped
  write, mod 16, in bits 7:4 of `REG_RW_MOT_DONE`.
  - Those bits were unused: libkipr `get_motor_done` and `wallaby_motor.c`
    mask the low 4 bits, and nothing on the Pi writes register 60.
  - The nibble is republished on every packet, because the main loop's
    `|=` on the done bits can write back a stale nibble.
  - The trade-off: a host write to register 60 can no longer set bits 7:4.
    The harness shows this is the only difference in `MASK_DONE_HI=0` mode.
- **A10, libwallaby:** `WombatDevice::transfer()` watches the nibble.
  - It ignores the first value, and treats a −1 step as the stale-nibble
    case above.
  - It logs `[core/wombat] [W]: co-processor rejected N corrupt SPI
    packet(s); some writes may have been lost` at most once per 5 s, and
    flushes anything pending when the device closes.
  - Older firmware never sets the nibble, so it never warns. Older libkipr
    ignores it.

### Host harness: `./harness.sh [base] [pr]`

Each test's falsifier is in brackets.

- **T1** All 65,536 `w8` frames are identical for addresses 3..152. [Any
  difference in `aTxBuffer`, the guard region, or the dirty flags.]
- **T2** The same for every `w16`/`w32` start address × 64 values.
- **T3** A read frame is identical.
- **T4** 200,000 random frames of 1..42 valid pairs are identical.
- **T5** Count-byte single-bit flips: PR never clears `'J'` and applies
  exactly the intended writes, except for flips to 0.
- **T6** Counts 5..255 over a zero-padded `w32` apply exactly the intended
  writes.
- **T7** Garbage frames with count > 42: blast radius.
- **T8** Never writes past `aTxBuffer`.
- **T9/T9b** Count 128..169 over a non-zero body (A9).
- **T10** The reject counter moves by exactly 1 per rejected frame and
  never on clean frames.

### H10: libkipr smoke test (`pr12_h10.py`, 2026-10-12)

Fix firmware `6896e00`, confirmed running by H6/H7/H8 before the test and
H6/H8 after. Bench supply (`power_level` reads 0.042), motors and servos on
ports 0 and 3, all ten digital ports empty. Every phase was run with stock
`/usr/lib/libkipr.so` 1.2.4 and with patched `libbuilds/pr12-rejects2`.
Each phase's falsifier also includes "the reject counter moves without an
injected bad frame".

Notes:
- The first `digout` run (`run-h10-active-patched-try1.txt`) failed
  because the test was wrong, not the firmware. It expected `digital()` to
  loop back a driven output and `set_digital_pullup` to stick. The firmware
  stops updating a pin's `DIG_IN` bit while it is an output
  (`wallaby_dig.c`, unchanged from master), and libkipr's pullup calls are
  stubs. The check now reads the OUT and OE registers instead.
- **By eye (the user, 2026-10-12):** the motors and servos on ports 0 and 3
  moved as expected, and digital sensors read properly.
- **Not covered:** the level on a driven output pin (`jumper` phase, needs
  a wire between two digital ports), and buttons and analog sensors changing
  under a person's hand.
- H10 was run on the fix only, not on PR 12 head `80ad31a`.
