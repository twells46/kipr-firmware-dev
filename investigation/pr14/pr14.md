# PR 14 regression check (`oscar/servo-power-off`)

Separate from the PR 8 investigation (`../investigation.md`) and the PR 12
and PR 13 checks (`../pr12/pr12.md`, `../pr13/pr13.md`). The same Wombat
rules apply: write the falsifier first, only one agent touches the Wombat,
never shut it down without asking, ask before flashing, and log what was
flashed.

PR 14 (`b470f8f`, two commits on `2776fb2`, by objorkman) makes
`disable_servos()` cut the 6 V servo rail:
- `init()` drives PE10 (`SRV_DISABLE`, open-drain, to U72's EN pin, which R52 pulls up
  to the battery) low first thing, before `init180MHz()`.
- `update_servo_power()`, once per main-loop pass, drives PE10 low 40 ms
  after bits 4–7 of `REG_RW_MOT_SRV_ALLSTOP` (61) are all set, and releases
  it as soon as any is clear.

**Question:** does a board, link or user program behave worse than on
master, and do the PR's own claims hold?

**Status 2026-10-28 19:35Z: static attack, register-level tests and the
at-the-robot tests that need no meter or scope (H2, H3 by eye, H4, H5,
H9) are done. Master is merged into the PR branch (`10314cc`, pushed), and
a re-check on that commit reproduced every earlier result. H1, H6, H7 and H8
need a meter, which the user doesn't have. The draft comment
(`pr14-comment.md`) has not been posted.**
- **H9 (motors): PR 14 moves the undervoltage window, it doesn't raise
  it.** On master a motor reversal within about 50 ms of `enable_servos()`
  trips the Pi's undervoltage flag on a weak pack (22/24, PR 14 0/24). On
  PR 14 the window moves to about 100–200 ms after the enable (D200: PR 14
  6/12, master 0/12). The same powered swing trips both images equally
  (AM 12/12 each). See "H9 verdict".
- **At the robot:**
  - **H2 PASS:** PR 14 makes disabled servos go limp; on master they
    keep holding.
  - **H5 CONFIRMED:** a re-enabled servo snaps back to the previous
    position at normal speed. A powered port with no pulses doesn't
    twitch.
  - **H3:** master does not centre servos at boot, which refutes C13's
    visible effect.
  - **H4 PASS on both images:** 30 four-servo power-ups at once, plus 30
    four-servo swings between 700 and 2300 µs. No STM32 reset, no lost
    frame, no Pi undervoltage, throttled stayed 0x0. C12 was not
    reproduced. This is not proof: the battery charge was unknown, the
    loads were light, there was no scope, and motors weren't run.
- **New finding (C20): with the deployed libkipr 1.2.4, no program exit
  disables the servos.** That covers return, `exit()`, SIGINT, SIGTERM and
  `shut_down_in`. libkipr's servo cleanup registration is lost at load
  (confirmed with gdb), and only `ao()` runs. So the PR's headline "when
  a program ends, the servos go limp" does not happen for student
  programs: the servos stay enabled and the rail stays on (L1, on master
  and PR 14). This is a libwallaby bug that predates PR 14.
- **C7 confirmed on hardware (S12).** A libwallaby-style
  `disable_servo(0)` read-modify-write across link slips wrote back all
  four disable bits 280 times. With servos 1–3 holding, that cut the rail
  5 times in 20 s (667 slips). On master the same writes only stop pulses.
  It needs a link slip, and a healthy link has none (P1).
- **The firmware itself passes everything:**
  - boot state;
  - release latency (≤ 1.1 ms);
  - the 40 ms cut (40.0–41.3 ms by firmware, 40.2–42.5 ms from the host,
    50 of 50);
  - partial patterns;
  - re-enable inside the window;
  - idle soak;
  - slips while disabled;
  - reset while powered;
  - pin reconfiguration.

  The merged image also passes PR 13's P1, P2 and P8.
- **The firmware change does what it says.** No code path reconfigures
  PE10, the pin and register names are right, the 40 ms wait leaves about
  17 ms of margin, and `usCount` wrap can't glitch it. The schematic
  confirms PE10 drives only U72 EN and VCC_6V0 feeds only the four servo
  ports, on both documented board revisions.
- **No hardware hazard found** (no short, nothing else on the rail).
- **The regressions are behavioural** (C8–C13 below):
  - parked servos now drop;
  - re-enabled servos snap to the previous program's last position;
  - four servos now power up and move together. H4 (no motors) saw no
    sag. H9 (motors) found the undervoltage window moves later, not up;
  - the rail no longer comes up at an STM32 reset. Master didn't centre
    servos at boot either (H3), so there's no visible change; whether one
    1.5 ms pulse goes out at reset is unverified without a scope.
- **Both link-level risks showed up on hardware (they need a link slip):**
  - C7 (S12, above): a misaligned read written back by libwallaby cuts the
    rail and drops every arm mid-run;
  - C6 (S8): the opposite case turns the rail on. That's the pre-existing
    A11 write-back from PR 13; the rail just follows it.

## Attack summary

Three read-only review agents covered firmware, board hardware (Eagle
netlists, AP65502/STM32/TXS0104E datasheets, the BOM) and the host side
(libwallaby `8cd0871`). None ran anything on the Wombat. I checked the
claims marked † myself.

Facts they rest on:
- **Servo timers:** TIM3 and TIM9 run at 1 MHz with a 20 ms period. ARR
  and CCR preload are on. The ISR writes the next CCR from `aTxBuffer` at
  each update, and a disabled port gets CCR 0 (constant low).
- **Bit mapping:** bit 4 = S0, 5 = S1, 6 = S2, 7 = S3.
- **Host side:**
  - libwallaby touches register 61 only in `set_servo_enabled` (a
    read-modify-write, `servo_p.cpp:21–35`) and `get_servo_enabled`.
  - Motor calls never write 61.
  - `r8` returns the reply byte even when the transfer failed.
  - Cleanup (`disable_servos`) runs on normal exit, SIGINT, SIGTERM and
    `shut_down_in`.
- **Rail:** U72 soft-start is about 13 ms (C60 0.1 µF). With no load,
  VCC_6V0 decays through R50+R51 (75 kΩ) on 69 µF, an RC of about 5 s.
- **Battery:** 2S. On a LiFePO4 pack or the 6 V bench adapter, U72 runs in
  dropout, so the rail sits at about 5.3–5.9 V, not 6.0 V.

## Tests

### On-Wombat (`pr14_hw.py`)

Run with `sudo python3 /tmp/pr14_hw.py [--reset] [--enable] <tests>`, with botui stopped.
- **`--enable`:** tests that clear a servo disable bit need it. They first
  centre all four position registers (1500 µs), so anything attached moves
  to centre. Without it, those tests SKIP.
- **Motors:** nothing commands a motor; motor bits 0–3 are only ever set.
- **Image:** the S tests need the diag image. The L tests run on any image.
  On the diag image they also check power.

### Test corrections made along the way

- **L4** first printed nothing: `os._exit` skipped flushing the child's
  stdout. It now prints with `flush=True`.
- **S6 on diag v1** failed on 2 of 20,000 frames. A capture showed real
  magnetometer data in the slots (`e41e 0031 fc22`: mag X high byte
  0xE4, which decodes as "power on"). `readIMU()` writes them before
  `update_servo_power()` in the same pass. Fixed in diag v2.
- **S2** read IDR from the pass that released the pin, before EN had
  risen. v2 samples IDR at the start of the pass, and S2 now waits 5 ms.
- **S10** can't see C7: its next toggle re-enables servo 0 long before
  40 ms. S12 holds the state the way a program does.

### H9: undervoltage under motor load (2026-10-28: done)

**What PR 14 adds to the supply:** on master the rail is always up, so an
enable only starts pulses into servos that are already powered and holding.
On PR 14 an enable also brings U72 up (about 13 ms soft-start into its
output caps and four servos' input caps), and four limp servos start from
wherever they drooped. The servos' travel current exists on both images; the
inrush and the from-limp start are new. H4 tried this with no motors, on a
battery of unknown charge, and saw nothing. That only means the system was
far from the Pi's threshold (about 4.63 V on the 3B+).

**Design: put the supply at the edge, then compare against master.**
- **Load stack:** three motors at raw PWM P (of 400) reversed at the event
  (about twice stall current), four servos swinging 700↔2300 µs, and four
  CPU busy loops at nice 19 so U73 draws more for the Pi.
- **Power ladder:** P = 0, 200, 300, 400. Somewhere on it the supply
  should cross from "no events" to "events", and a shift of that edge
  between images is the PR 14 effect. P = 0 is the H4 condition.
- **Cells, shuffled within blocks with a fixed seed** so each image gets
  the same sequence: A0 (enable + reverse in one frame), A20 (reverse 20 ms
  after the enable, when servo start current begins), B (reverse only:
  supply control), C (enable only, motors steady: the power-up alone).
  Servos are disabled 0.7 s before every event, so on PR 14 the rail is
  fully collapsed each time.
- **Detectors, per cycle:** `vcgencmd get_throttled` bit 0, polled about
  every 3 ms (2.8 ms per call on this Pi). Also lost SPI frames, an STM32
  reset (motor or servo registers not as written), and on diag2 `ons`, which
  proves the rail actually cycled. dmesg is counted per level.
- **Order:** master (flashed now) → diag2 → master. The two master runs
  bracket battery drain. B rates show whether the supply was comparable.
- **Stop rule:** a level and the ladder end if bit 0 stays set 2 s or shows
  in 5 cycles in a row.

**Verdict, fixed before running:**
- **Regression:** pooled A+C undervoltage rate on PR 14 above both master
  runs (one-sided Fisher p < 0.05 for each), with B not different
  (p > 0.2). Also any STM32 reset, or a Pi reboot, on PR 14 only.
- **Not reproduced, with sensitivity:** some level has master B or A
  events in some but not all cycles (the supply was at the edge), and
  PR 14's A+C rate is not above master's.
- **Not reproduced, no sensitivity:** no events on any image at P = 400.
  Then rerun on a weaker supply.

**Known bias:** in B on master the disabled servos still hold (powered),
but on PR 14 they're unpowered. PR 14's B is slightly lighter, so a lower B
rate on PR 14 doesn't mean the supply was stronger.

**Design changes made while running (v3, current `pr14_uv.py`):**
- `get_throttled` bit 0 stays set for 3.23 s after one dip (measured 18 of
  18 times), so a cycle now counts only an onset. Each event waits until
  bit 0 clears.
- The battery drifted too fast for comparisons between runs: P = 300 gave
  0/48 events in master1 and 19/34 in m1 four minutes later. Cells M and AM
  were added as matched controls inside each image (the same full swing with
  the servos enabled and holding through OFF, so the rail is up on both
  images). A20 was dropped. On master C should equal M and A0 equal AM; on
  PR 14 the gaps C − M and A0 − AM are the PR's added load, on the same
  battery in the same minutes. `compare` prints these pairs.
- Ladder 200, 250, 300; stop after 10 onsets in a row.

**H9 verdict:**
- **PR 14 doesn't raise the peak risk; it moves it.** The trip needs the
  servos' start current and a motor reversal at the same time. On master
  the servos are already powered and start drawing as soon as pulses
  begin, so the bad window is a reversal within about 50 ms of
  `enable_servos()`. On PR 14 their current comes about 100–200 ms later
  (U72 soft-start, then the servos' own boot), and the window moves there.
  At the worst delay both images trip every time (6/6).
- **New exposure (real, measured):** a program that starts or reverses
  motors about 100–200 ms after enabling the servos now trips undervoltage
  where master didn't (D200 6/12 vs 0/12). A program that does it at once
  is now safer (0/24 vs 22/24). Over the timings tested, PR 14 tripped less
  often overall.
- **Shared risk, not new:** on a weak pack, a four-servo swing landing with
  a motor reversal pushes the Pi under 4.63 V on both images. On pack 1
  this ended in a boot loop on master (`m2`, then the pack died).
- C12 is therefore reproduced as a timing shift, not as a larger sag. What
  the Pi sees is the undervoltage flag (and throttling). No STM32 reset or
  Pi reboot was tied to PR 14.

**Hazards:** motors reverse at full power every 1.5 s, so the wheels must
be off the ground. If the Pi browns out and reboots, nothing stops the
motors (`../pr13/a9.md`), so someone must be at the power switch. A hard
brownout risks the SD card.
