# A9: one-byte-short transfer starves the main loop

Follows on from `pr13.md` (A9, P12). Same Wombat rules: falsifier first,
one agent on the Wombat, ask before flashing, log every flash.

**Status 2026-10-12 21:35Z: mechanism confirmed, fix F1 tested, committed
locally on `oscar/spi-resync` as `4a731ea`, not pushed (the user wants the other regression fixed first). The motor
run passed on the fix image** (see "Motor run"). Results are at the end; the plan below is as
written before any run.

## Plan (written before the runs)

**Goal:** confirm the A9 mechanism by direct measurement, then test one fix
on master and on the PR 13 merge.

## What is known and what is inferred

- **Measured (P12, 6 of 6 on master and PR 13):** after a transfer of 88 or
  177 bytes the reply repeats (5–9 distinct of 40) and the link never
  recovers.
- **Inferred from code, never observed:** the cause is
  `DMA1_Stream4_IRQHandler` re-entering on a lone TX transfer-complete flag
  that `handle_dma()` won't clear (`wallaby_dma.c:291`).

Reading the code for this plan adds three points, all still inference:

1. **TX completes before RX in every frame, not only in the stuck state.**
   The same model that explains P12 (TX has written one more byte than has
   started shifting) puts TX's flag at the start of byte 87 of a healthy
   frame and RX's at the end of byte 88. So the Stream4 interrupt already
   re-enters for about 2 byte times per healthy frame: about 1 µs at
   16 MHz, 32 µs at 0.5 MHz.
2. **"Clear the lone flag" (`pr13.md`, Next 2) would break a healthy
   link.** If the handler clears a lone TX flag, both flags are never set
   together and no frame is ever processed.
3. **The timer interrupts are starved too.** Every interrupt is at
   priority 0, and Stream4 (IRQ 15) is serviced ahead of TIM1_CC, TIM8_CC,
   TIM3 and TIM9 (IRQ 24–46). Those handlers copy the motor PWM and servo
   registers into the timers, so in the stuck state outputs are frozen in
   the interrupt path as well as the main loop.

Only one residue is fatal: at idle TX is exactly one count ahead of RX, so
a lone TX flag spans the idle gap only when RX stops at 88 mod 89.

## Fix candidate F1

Process a frame on the RX flag alone, and don't enable the TX stream's
transfer-complete interrupt:
- `handle_dma()` tests and clears `DMA_FLAG_TCIF3` only;
- drop `DMA_ITConfig(DMA1_Stream4, DMA_IT_TC, ENABLE)` (in
  `spi2_dma_start()` on PR 13, at its boot-time site on master).

Expected effect: frames are processed at the same instant as now (the
moment both flags are set is always the RX flag's moment, by point 1), no
interrupt can stay pending, and after a one-byte-short transfer the main
loop keeps running. On PR 13 the count check then sees chip select high
with the RX count at 1 and resyncs. On master the link stays slipped, as
it does for any other wrong length, but the robot keeps running.

Not pursued: running the resync from the interrupt (larger change, and it
doesn't help master); changing interrupt priorities (the handler would
still spin).

**Diag v2** extends `make-diag-patch.py`. Reading counters in the stuck
state needs a decoder that finds the `0xD3` item at any rotation, since
replies are offset by one byte there. That goes into `pr13_hw.py`.

**P15 (new): one byte short, host idle.** Send 88 bytes, send nothing for
1 s, then frames 20 ms apart. Also n = 177, 266, and the 88 at each of the
four clocks.
- Fails on merge + F1 if the first frame after the pause is bad, if
  `passes` moved by less than 95% of a healthy second, or if `reset`
  moved by other than 1.
- Fails on master + F1 if `passes` moved by less than 95% of a healthy
  second. (The link staying slipped is expected there.)

**E3 pass criteria**
- P12 on merge + F1: lost ≤ 25 and distinct replies ≥ 80% of healthy, 6 of 6.
- P12 on master + F1: distinct replies ≥ 80% of healthy; no recovery expected.
- P1, P2: as before, plus `tx_only`/`rx_only` handler entries at 0 (the TX
  interrupt is off) and loop rate not below the unfixed image.
- P3–P11 and H1–H8: same verdict as the unfixed image. P11 is expected to
  stay FAIL (A11 is a host-side issue).
- P8 (boot while polling) ×10 rather than ×5, since F1 touches the enable
  sequence.

**Ways F1 could regress, to check before flashing**
- Something else reads or depends on the TX flag: grep both trees;
  `spi2_dma_cleanup()` is the only user I've seen.
- Why both flags were required originally: `git log -S` on the condition
  in Wombat-Firmware and its upstream history.
- PR 13's reset path pends both stream interrupts when it disables them
  (A3); confirm `DMA_DeInit` still leaves nothing pending with the TX
  interrupt disabled.

## Order and stopping points

2. Build diag v2; **ask**, flash, E2. If either falsifier fires, stop and
   rework the model before any fix image is built.
3. Build the three F1 images; **ask**, flash, E3 and E4.
4. Write results into `pr13.md` (A9 section, test table, log). Restore
   `builds/pr13-merge-master` or whatever the user wants left on the unit.
5. The user decides where F1 goes. A9 is on master, so my suggestion is a
   small PR against master rather than a change to PR 13, plus a note on
   PR 13 that its n = 88 claim depends on it. Nothing is posted or pushed
   without a fresh go-ahead.

## Out of scope

  F1 removes it; if not, it needs the TX/RX-count-at-reset image.
- A11 (libwallaby ignoring `transfer()`'s result).
- A motor-running check of the frozen-output consequence. Worth one run
  with a motor on the bench if the user wants it shown.

## Motor run

**Done on the fix image (`a9-f1`), 21:43Z: PASS, 9 of 9.** Each rep runs
the motor(s) at 25% for 1.5 s, sends the 88-byte transfer, calls `ao()`,
leaves the host idle for 2 s, then reads the position counter twice 0.5 s
apart.

| Run | Result |
|---|---|
| `mot0`, port 0 alone ×3 | link recovered, mode and direction registers cleared, drift 0 counts |
| `mot3`, port 3 alone ×3 | the same |
| `mot`, ports 0 and 3 together ×3 | the same |

- Running speed before the slip was about 102,000 raw counts/s (gmpc about
  607 per 0.5 s) in every rep.
- The check is made 2 s after `ao()`, so it shows the motors stopped
  within 2 s, not how fast.
- The Pi logged one more "Undervoltage detected" during the two-motor run
  (count 2 → 3) and did not reboot. The user says the bench adapter only
  supplies 6 V, so undervoltage under motor load is expected on this
  setup and probably unrelated to the firmware.
- Not run on unfixed firmware beyond the attempt below.

**Earlier attempt, unfixed firmware.** One attempt on the unfixed `a9-diag2` image at about 21:00Z went
wrong:

- `mot` started motors 0 and 3 at 40%, sent the 88-byte transfer and called
  `ao()`. The Pi then rebooted (`dmesg` on the next boot: "Undervoltage
  detected" at 21 s and 88 s; `vcgencmd get_throttled` 0x50000). The test's
  result line was lost with it.
- The STM32 was not reset by the Pi's reboot. The motors kept running for
  about 100 s, until I stopped them with `ao()` at about 21:02:20Z. The
  motor mode and direction registers still held the test's command, so
  the earlier `ao()` calls had not been applied.
- The test relies on the Pi to pulse the STM32 reset line, so a Pi reboot
  mid-test leaves nothing to stop the motors on unfixed firmware.
- `mot` was then corrected (libwallaby swaps ports 2 and 3; default power
  25%; `mot0`/`mot3` run one motor) before the run above.
