# PR 13 regression check (`oscar/spi-resync`)

Separate from the PR 8 investigation (`../investigation.md`) and the PR 12
check (`../pr12/pr12.md`). The same Wombat rules apply: write the falsifier
first, only one agent touches the Wombat, never shut it down without
asking, ask before flashing, and log what was flashed.

PR 13 (`78637f2`, two commits on `80ad31a`) adds
`spi2_dma_check_sync()`, called once per main-loop pass. It resets SPI2 and
both DMA streams, with interrupts off and only while chip select is high,
when any of these holds:
- chip select is high and the RX stream's count isn't 89 (confirmed 2 µs
  later);
- `handle_dma()` saw a frame without `'J'` at byte 0 or `'S'` at byte 88;
- SPI2 reports an overrun.

It also moves the boot-time enable sequence into `spi2_dma_start()`.

**Question:** does a link or a board that worked before behave worse, and
do the PR's own recovery claims hold?

**Status 2026-10-12 20:45Z: attack done, tests run on hardware.**
- **Healthy link: no regression.** P1 and P2 pass with every resync
  counter at 0, and the PR 12 set (H1–H8) passes on the merged image.
- **Recovery works for most slips** (P3–P5, P7, P9): 2–3.5 transfers lost
  on average, 10 at worst, none after a 10 ms pause, and no stray register
  change. Master recovers from none of them.
- **Three failures on PR 13:**
  - **A9, confirmed.** A transfer one byte short of a frame (88, 177) is
    never recovered, and the main loop is starved (P12, 6 of 6). The
    starvation is the same on master; the PR's test plan expects n = 88 to
    recover.
  - **A10, confirmed: a regression.** About 0.3% of resets leave the link
    stuck with the main loop starved (36 of 12,000 events in P13/P14 on
    the diag image). Most are visibly dead (no `'J'`). About 1 in 7 are
    **silent**: replies look valid, but every write is dropped and sensor
    values barely update. An unframed frame that master ignores (0 stuck
    in 3,000) can therefore kill the link on PR 13.
  - **A11, confirmed at the raw-frame level.** A read taken during a
    resync and written back corrupted the register after 145–155 of about
    640 slips (P11). On master the write-back can't land.
- **Smaller:** a frame split across chip select (P10) trips the count
  check about 1 time in 200; no stock host sends one.
- **Update 21:35Z: A9 is root-caused and has a tested fix; see `a9.md`.**
  With it, P12 passes and P13/P14 show 0 stuck links in 18,000 events, so
  A10 did not reproduce either. A11 and P10 are unchanged. The fix is
  commit `4a731ea` on the local `oscar/spi-resync`, not pushed.
- Currently flashed: `builds/a9-f1` (PR 13 merge + the A9 fix), link healthy.

## Attack summary

Three read-only review agents (firmware concurrency, STM32 peripheral
semantics, host side). None ran anything on the Wombat. Timing figures are
their estimates from instruction counts; P7 measured the interrupts-off
window at 5.5 µs at most.

Facts they rest on:
- HCLK 180 MHz, APB1 45 MHz. SysTick fires at 1 MHz and increments
  `usCount`, so `delay_us(2)` waits 1–2 µs and `usCount` stops while
  interrupts are off.
- `NVIC_PriorityGroupConfig` is never called: every peripheral interrupt
  is at priority 0 and SysTick at 15. Any interrupt that keeps re-entering
  stops `usCount` and the main loop.
- `handle_dma()` clears the two transfer-complete flags only when both are
  set (`wallaby_dma.c:290`, `356`).
- SPI2 is a hardware-NSS slave (`SPI_NSS_Hard`), so it ignores SCK while
  chip select is high.
- libwallaby sends one 89-byte message per call at 16 MHz (about 45 µs),
  with `'J'`, version 4 and `'S'` at byte 88, then `usleep(50)`. Its
  `r8/r16/r32` return the reply bytes even when byte 0 isn't `'J'`, and
  `w8/w16/w32` never retry (`wombat_device.cpp:58–130`, `165–169`).
- Nothing else on the Pi uses spidev: botui goes through libkipr, and the
  wombat-os scripts use GPIO 17/23, the UART and I2C.

### A9 in detail

The TX stream runs one byte ahead of RX, because the next reply byte is
preloaded. After a transfer of 89k + 88 bytes, TX has completed a frame
and RX is one byte short:
1. TX's transfer-complete flag is set alone. `handle_dma()` returns
   without clearing it, so `DMA1_Stream4_IRQHandler` re-enters at once,
   forever. The main loop and SysTick stop.
2. The next transfer's first byte completes RX, both flags clear, and the
   loop runs. TX completes again at the start of that transfer's last
   byte, before chip select rises.
3. So the main loop only runs while chip select is low. PR 13's count
   check and its reset both require chip select high, and the 60 µs wait
   uses `usCount`, which is stopped.

This predicts, on every firmware, that the main loop is starved while the
host is idle (no PID, back-EMF, ADC, digital or IMU updates; motors hold
their last PWM), and that PR 13 does not resync. On base the only way out
is an STM32 reset.

without `'J'`; "silent" means valid-looking replies with the write not
applied. A stuck link got 300 more frames before it was counted.

### What the stuck states look like (A10)

- Every stuck link had a starved main loop: 5–12 distinct replies of 40,
  against 40 when healthy. That is the A9 signature.
- 31 of 36 were dead and 5 silent. In the silent state the host sees
  `'J'`, the right version and 0 desyncs, so libwallaby logs nothing. In
  the one run where it was found by accident, `pr12_hw.py` then failed H2,
  H3 and H8 (writes ignored) while H1, H5 and H6 passed.
- A single 1-byte transfer brought a silent link back (seen once).
  Otherwise only an STM32 reset does.
- P7 and P9 can't see these states: their next wrong-length transfer
  knocks the link out of them again.
- The mechanism of the silent variant is not established. It needs TX
  aligned with the host and RX behind it, which the agents' model of the
  reset race (A10) does not produce. The diag counters at the time show
  `frame` far ahead of `reset`, i.e. frames keep arriving unframed while
  the reset can't run.

### Test corrections made along the way

- P3's stray-register check first flagged byte 87 on master, a sensor
  value that drifts. The check now covers only the start byte, version and
  the host-written block (61–85).
- P11 first counted every later reply as wrong after its own first
  corruption. It now restores the register and counts corruptions.
- P13 first detected only dead links. It and P14 now run the health check
  after every event; the earlier counts are in `run-merge-diag-2.txt`.
- The first PR 12 run on the merged image started on a link left silent
  by the PR 13 tests. `run-merge-master-pr12set.txt` is the rerun from a
  fresh flash.

Not tested: `pr12_h10.py` (motors and servos) on the merged image; a
glitch on SCK or chip select; the MISO level while SPI2 is in reset; any
libkipr-level check of A11 (P11 emulates libwallaby's calls with raw
frames).
