# A10: a resync that races a host frame leaves the link stuck

Follows on from `pr13.md` (A10, P13, P14) and `a9.md` (fix F1). Same Wombat
rules: falsifier first, one agent on the Wombat, ask before flashing, log
every flash. No motor run on unfixed firmware (`a9.md`, "Earlier attempt").

**Status 2026-10-13 15:10Z: done through step 6. F1 is the fix for A10.**
- **How a reset ends stuck (goal 1), measured:** SPI2 comes up inside
  byte 0 or byte 1 of a host frame. The TX stream then ends the frame
  ahead of the RX stream (counts 88 / 1, 89 / 1 or 89 / 2), a lone TX flag
  spans the idle gap, and the loop is starved. 88 / 1 is the silent state;
  the other two are dead. Natural and injected stuck links show the same
  three states and no others.
- **F1 is the whole fix (goals 2 and 3):** on the F1 image 5,609 injected
  races, 706 of them into those three states, all recovered after one
  more reset. Soak on the plain fix: 0 stuck in 60,000 events. No further
  firmware change is needed for A10.
- One residual, not measured, and one plan hypothesis that was false as
  worded (H4): see B6.
- `a9-f1` is back on the unit, link healthy.
- Step 7 is prepared, not sent: `4a731ea` is a fast-forward of
  `origin/oscar/spi-resync` (`78637f2`), and the follow-up comment is
  drafted in `pr13-comment-2.md`. The user confirmed on 2026-10-13 that
  A10 was the regression the push was waiting for. Pushing and posting
  still need the word.

The plan below is as written on 2026-10-12; results and deviations are in
the sections after "Order and stopping points".

## Goal

1. Establish by measurement how a reset ends in the dead state and in the
   silent state. Both are inference today.
2. Decide whether F1 (`4a731ea`) is the whole fix for A10, or only removes
   the starvation that made the stuck states permanent.
3. If something survives F1, find the smallest further change and test it.

## What is known and what is inferred

**Measured**
- Unfixed PR 13: 36 stuck links in 12,000 events (31 dead, 5 silent), all
  with a starved main loop (5–12 distinct replies of 40). Master: 0 in
  9,000.
- With F1: 0 stuck in 18,000 events (about 54 expected at the old rate).
- In the three silent cases with counters, `retry` was 2.1%, 2.5% and 0.8%
  of `reset` (24/1131, 10/396, 2/257), and `frame` ran about 300 ahead of
  `reset`, i.e. every frame sent to the stuck link was seen as unframed.
- A 1-byte transfer cleared a silent link, once.
- The rate depends on the image: 10 per 3,000 on diag, 0 per 3,000 in the
  one P13 run on plain merge, yet plain merge died in P6 (2 of 3) and P8
  (1 of 5).

**Inferred, never observed**
- The race: chip select falls during the 5–8 µs interrupts-off reset, so
  SPI2 is enabled part-way into a frame. 5.5 µs in a 220 µs frame period is
  2.5%, which matches `retry`. Stuck at 0.3% then means a window of about
  0.7 µs, and silent a window of about 0.1 µs: one or two bit times at
  16 MHz. That points at bit-level phase, not just byte count.
- Dead: SPI2 comes up inside byte 0, RX ends the frame with 88 bytes and TX
  with 89, which is the A9 state. `spi_resync` is set but the loop is
  starved.
- Silent (new for this plan, from the counters): TX is aligned with the
  host and has completed (lone TX flag across the idle gap, so the loop
  starves), and RX is m bytes behind. Each frame, RX completes at byte m,
  the handler finds a rotated frame and drops it (`frame` +1, `cslow` +1),
  and TX completes again before chip select rises. The 1-byte cure fits
  only m = 1, so TX is **two** ahead of RX instead of one. What loses the
  RX byte (or spends the extra TX byte) is unknown.

**Not known**
- Whether F1 prevents these states or only lets the count check clean them
  up. With F1 the race still happens; `retry` should still be about 2%.
- Whether a state exists that F1 does not leave. The count check reads the
  RX count only. A state with RX at 89 and TX off by one or more would have
  the host reading garbage, the firmware seeing framed frames and applying
  writes, and nothing triggering a resync. Not seen; not excluded by
  18,000 random events if its window is a few nanoseconds wide.

## Hypotheses

| # | Claim | Wrong if |
|---|---|---|
| H1 | Dead = SPI2 enabled inside byte 0 of a frame; at chip-select rise RX count is 1 and TX has completed | a natural dead state shows any other pair of counts |
| H2 | Silent = TX two ahead of RX (RX count 1, TX count 88, reply byte 0 is `'J'`) | a natural silent state shows other counts, or the loop isn't starved by a lone TX flag |
| H2a | The extra TX byte comes from a partial byte: SPI2 enabled mid-byte, chip select rises with bits left over, the slave keeps its bit count and TX has already preloaded | silent appears at a whole-byte phase, or disappears when frames end on a byte boundary relative to the enable |
| H2b | An RX byte is lost to an overrun or to the request being enabled after the byte arrived | `OVR` clear and the SR/NDTR trace shows equal request counts |
| H2c | The race is at another stage: chip select falls between the stream disables and the SPI reset, not at the enable | silent only reproduces at the enable stage |
| H3 | With F1 every state the race can produce is left by the count check within one extra reset | any (stage, phase) cell stays bad after 300 frames, or fails the health check, on the F1 image |
| H4 | No reachable state has RX count 89 at idle with TX misaligned | any cell shows it |

## Method: make the race deterministic

Random traffic hits the window 0.3% of the time and the host can't aim at
a 5 µs window. So the firmware aims instead.

**Injection image** (`a10-inj.patch`, on top of `pr13-diag.patch` and
`a9-diag2.patch`):
- **Arming.** An unframed frame with byte 0 = `0xA1` and bytes 1–3 = stage,
  delay high, delay low arms one injection. It sets `spi_resync` like any
  unframed frame. Nothing else in the image changes unless armed.
- **Hold.** In the armed reset, at the chosen stage, spin with interrupts
  off until chip select is low, then for `delay` CPU cycles (5.6 ns each;
  one bit at 16 MHz is 11 cycles), then carry on. Give up after 50 ms and
  count it (`inj_timeout`).
- **Stages:** S0 before the stream disables; S1 between them; S2 before
  `SPI_I2S_DeInit`; S3 before `DMA_DeInit`; S4 before `SPI_Init`; S5 before
  the stream enables; S6 before the DMA requests; S7 before `SPI_Cmd`; S8
  after it, before `spi_resync = !cs`.
- **Snapshot.** Latched once per reset at the first of: the next
  `spi2_dma_check_sync()` entry with chip select high, or the first
  `handle_dma()` entry after the reset. TX count, RX count, SPI2 SR, the two
  transfer-complete flags, `spi_resync`. A second latch after frame 2.
- **Publishing.** Through the existing `0xD3` item channel. In a starved
  state the per-pass publisher only runs while chip select is low (it worked
  for E2b with the rotation decoder); if that is too slow, publish from
  `handle_dma()`.

`pr13_hw.py` gains `inj(stage, delay)`: arm, wait 5 ms, send one good
frame (this is the frame the reset races), wait 10 ms, read the snapshot,
then classify: healthy / recovered after k frames / dead / silent / other,
using the existing `health()` and `liveness()`. `--reset` pulses the STM32
after any stuck cell.

Timing resolution: the hold loop's jitter is a few cycles, about half a bit
at 16 MHz. So map at 1 MHz (bit = 180 cycles) and 4 MHz first, then confirm
the interesting cells at 16 MHz with repeats.

## What counts as the solution

- **H3 and H4 hold (B6 and B7 clean):** F1 is the fix for A10. A10 was the
  race landing in a state the starved loop couldn't leave, and the write-up
  says which phases produce it and that each costs one extra reset. No
  further firmware change.
- **B6 finds a cell F1 doesn't leave:** stop, write the state down from its
  snapshot, and only then pick a change. Candidates I'd expect to matter,
  none to be built before that:
  - F2: the idle check also requires the TX count to be 88 (covers H4's
    state and any TX/RX disagreement).
  - F3: enable SPI2 only after re-checking chip select, and treat a fall
    during the reset as "reset again" without relying on the next pass.
  Each would be tested on the failing cell first, then B6's grid, B7, and
  P1–P15 plus H1–H8 for regressions.
- **B2 or B3 falsifies H1/H2:** the model of the stuck states is wrong.
  Rework it from the snapshots before running B6; a clean B6 on a wrong
  model isn't evidence.

## B1: desk check (written 2026-10-13, before B2)

Counting model, each line an assumption the snapshots can contradict:
- **M1.** TXE is set out of reset, so the TX stream writes buffer byte 0 to
  the data register as soon as its request is enabled, before SPI2 is.
- **M2.** When the slave starts shifting a byte (its first clock after the
  enable) the data register moves to the shift register and the stream
  writes the next byte. So TX writes = bytes started + 1.
- **M3.** RX stores one byte per 8 clocks counted from the enable.
- **M4, unknown.** At chip-select rise with a byte part-shifted, the slave
  either (a) drops it and starts the next frame on a fresh byte loaded from
  the data register, or (b) keeps its bit count, so every later byte is
  bit-shifted.

Starvation rule for unfixed firmware, from the same model: with RX count m
and TX count t at idle (t = 89 with the flag set means TX just completed),
a lone TX flag spans the idle gap exactly when t > m. Healthy is m = 89,
t = 88.

S7 (hold before `SPI_Cmd`), by where the enable lands in the raced frame:

| Enable lands | Slave sees | RX | TX | Reply seen by host from frame 2 | Unfixed | F1 |
|---|---|---|---|---|---|---|
| chip select low, before the first clock | 89 bytes | 89 | 88 | aligned | healthy; raced frame applied; `retry` +1, so one more reset after it | same |
| inside byte 0 | 88 bytes + bits | 1 | 88, flag set | M4a: aligned (`'J'` at 0), RX one behind: **silent**. M4b: bit-shifted: **dead** | starved (88 > 1) | recovers: `reset` +2, `retry` +1 |
| between bytes 0 and 1 | 88 bytes | 1 | 89, flag set | rotated one byte (`'J'` at 1): **dead** | starved | recovers |
| inside byte 1 | 87 bytes + bits | 2 | 89, flag set | M4a: rotated one byte: **dead**. M4b: bit-shifted: **dead** | starved (89 > 2) | recovers |
| between bytes b and b+1, b ≥ 1 | 88 − b bytes | b + 1 | b | rotated | not starved; frame 2 unframed; reset; healthy | same |
| inside byte b, 2 ≤ b ≤ 87 | 88 − b bytes + bits | b + 1 | b − 1 | rotated or bit-shifted | not starved; reset; healthy | same |
| inside byte 88 | bits only | 89 | 87 | M4a: rotated one byte with RX aligned (**H4's state**). M4b: bit-shifted | not starved; `retry` reset clears it | same |
| after the last clock, chip select still low | nothing | 89 | 88 | aligned | healthy; `retry` +1 | same |

What this predicts beyond the plan's table:
- The stuck zone is two bytes wide: first clock of byte 0 to last clock of
  byte 1, about 1 µs at 16 MHz, 0.45% of a 220 µs frame period (measured
  stuck rate 0.3%).
- Three count pairs in it, not two: (1, 88), (1, 89) and (2, 89). H1 and
  H2 as written cover the first two. A natural stuck link with RX = 2,
  TX = 89 fits the model and doesn't falsify H1.
- Silent can only come from "inside byte 0" under M4a. Under M4a dead to
  silent would be about 9 : 7; under M4b there is no silent state at all.
  Measured was 31 : 5, which fits neither, so M4 is probably
  phase-dependent within the byte. B3's quarter-bit sweep is what resolves
  it.
- With F1, every state reached with chip select low is cleared by the
  `retry` path (`spi_resync = !cs` at the end of the reset) on the next
  pass, whatever the counts. The count check is a second route for all but
  the "inside byte 88" row. So H3 predicts `reset` +2 and `retry` +1 in
  every chip-select-low cell; `count` +1 except in the byte-88 row.
- H4's state exists in the model (inside byte 88, M4a) but only until the
  `retry` reset. It would persist only if chip select rose in the few
  cycles between `SPI_Cmd` and the `!cs` read with clocks still running,
  which a host that raises chip select after the last clock can't do.

## Step 2: injection image and script (2026-10-13)

| Image | Patches on `a8cd96c`, in order | md5 |
|---|---|---|
| `builds/a10-inj` | `pr13-diag`, `a9-diag2`, `a10-inj` | `68f85841…` |
| `builds/a10-f1+inj` | `a9-f1`, `pr13-diag`, `a9-diag2`, `a10-inj` | `2811d480…` |

`make-a10-patch.py` generates `a10-inj.patch`; applying the patch to the F1
tree gives the same source as running the generator on it.

Deviations from the method above:
- **Delay is 24 bits** (arming bytes 2–4), not 16: a frame at 1 MHz is
  128,000 cycles. Byte 1 is the stage.
- **S5 sits between `spi2_dma_init()` and `spi2_dma_start()`**, i.e. before
  the two `DMA_ITConfig` calls as well as the stream enables. Those calls
  are inert on a disabled stream, and it keeps one patch valid for both
  trees.
- **Snapshots are taken for every reset, not only armed ones**, in two
  sets: `inj_*` for the last armed reset, `nat_*` for the last reset of any
  kind (B2's natural captures). Each set has three looks: `end` (last
  thing inside the reset), `l1` (first look with chip select high
  afterwards), `l2` (the same after one more chip-select-low period). The
  looks are made on entry to `spi2_dma_check_sync()` and `handle_dma()` and
  just before a reset. With F1, `l2` is normally after the cleanup reset.
- **`en`** is added: cycles from chip select seen low to the end of the
  reset. It places stages other than S7 on S7's delay axis (B4).
- 16 new items on the `0xD3` channel (37 in all), so a full read takes
  about 40 passes.

Unarmed cost, by reading the patch: nine stage tests of a few cycles each
before the enable (about 0.2 µs on a 5.5 µs reset), a state test on each
entry to `spi2_dma_check_sync()` and `handle_dma()`, and the `end` snapshot
after SPI2 is enabled. B2's P1 and stuck rate are the measured check.

`pr13_hw.py`: `inj:STAGE:HZ:START:STOP:STEP:REPS` (one `INJ` line per
injection: class, lost frames, snapshot, counter deltas, reply offset in
bits, and whether a 1-byte transfer cleared a stuck link), `b2`, `b7`, and
the snapshot plus reply offset for every stuck link in P13/P14. Dry run on
`a9-f1`: `run-a10-b0-script-check.txt`.

## Results

Snapshots are written TX count / RX count, taken at the first look with
chip select high after the reset (`l1`). "Reply offset" is the (byte, bit)
at which `'J'` and the version appear in a reply; (0, 0) is aligned.

### B2: unarmed injection image, natural stuck links (`run-a10-b2.txt`)

Flashed `a10-inj` at 13:53Z. P1 2,000 frames: clean, all resync counters 0.
P13 and P14, 3,000 events twice each: 13, 9, 13 and 11 stuck, **46 in
12,000 (39 dead, 7 silent)** against 36 in 12,000 on the diag image. The
injection code is inert enough.

| Class | Snapshot | Reply offset | After a 1-byte transfer | Count |
|---|---|---|---|---|
| silent | 88 / 1, TX flag set | (0, 0) | healthy | 7 |
| dead | 89 / 1, TX flag set | (1, 0) | healthy | 30 |
| dead | 89 / 2, TX flag set | (1, 0) | silent | 5 |
| dead | not read | (1, 0) | healthy 3, silent 1 | 4 |

- **H2 holds** as written: every silent link is TX two ahead of RX
  (88 / 1), reply aligned, loop starved by a lone TX flag.
- **H1 holds for 30 of 35 dead links and is too narrow for 5**: those have
  RX = 2. B1's table predicted that third pair before the run. All three
  pairs satisfy the starvation rule (TX count > RX count).
- No reply was bit-shifted: a part-shifted TX byte is dropped at
  chip-select rise (M4a for TX).
- **The plan's B5 prediction "1 byte cures silent and not dead" was
  wrong.** One byte moves 89 / 1 to 88 / 89 with both flags handled, so the
  loop runs and the pending resync fires: cured. It moves 89 / 2 to 88 / 1,
  which is the silent state. The model explains both; the plan's sentence
  was written before the model had the dead counts.

### B3: S7 sweep at 1 MHz, unfixed (`run-a10-b3-cal.txt`, `run-a10-b3.txt`)

2,547 injections: delay 600–5,600 cycles in steps of 60, 198,000–209,000
in steps of 90, and 5,600–198,000 in steps of 300, 3 reps each.

Two things about the method, found in the calibration run:
- **The host's timing isn't steady enough for the delay to fix the phase.**
  Chip select to first clock is about 800 cycles (4.4 µs) with jitter of a
  bit or more, and the Pi's "1 MHz" is about 2,300 cycles per byte
  (0.62 MHz). So the phase is read from the raced frame's own reply: the
  (byte, bit) at which `'J'` appears is where the slave started. That
  gives bit resolution, not the quarter bit the plan asked for.
- **M2 needed one addition, M5.** A slave enabled mid-byte starts its
  first TX byte in one of two ways: at once, or after one dummy byte of
  zeros (8 clocks, no write to the data register). Enabled before the
  first clock it always starts at once. About half and half at this clock.
  What picks the mode is not established (the SCK level at the enable is
  my guess; the jitter hides it).

| Enable lands | TX start | n | Snapshot | Result |
|---|---|---|---|---|
| chip select low, before the first clock | at once | 9 | 88 / 89 | healthy; `reset` +2, `retry` +1 |
| at the first clock edge | dummy byte | 4 | 89 / 89, flags handled | **H4's state**: frame received whole, reply rotated one byte. Cleared by the `retry` reset |
| inside byte 0 | at once | 44 | 88 / 1, TX flag | **silent**, 44 of 44 |
| inside byte 0 | dummy byte | 43 | 89 / 1, TX flag | **dead** |
| between bytes 0 and 1 | either | 20 | 89 / 1, TX flag | **dead** |
| inside byte 1 | at once | 53 | 89 / 2, TX flag | **dead** (1 byte turns it silent) |
| inside byte 1 | dummy byte | 52 | 1 / 2 | recovers |
| byte 2 to byte 86 | either | 2,035 | RX < 89, TX ≤ RX | recovers, all of them |
| last two bytes, or after the frame | — | 338 | 15 are 87 / 89 (the B1 byte-88 row), 68 came after chip select rose | recovers, all of them |

- Every stuck cell lies between the first clock of byte 0 and the last
  clock of byte 1, as B1 predicted, and every snapshot in it is one of the
  three pairs B2 found on natural stuck links. **The injected states are
  the natural ones.**
- Every stuck snapshot has TX count > RX count and every recovered one
  doesn't: the starvation rule held in 2,547 of 2,547 (6 stuck links
  whose counters couldn't be read are counted by their reply offset and
  1-byte result).
- Dead and silent are the same race half a bit or a byte apart. Silent is
  the "at once" start inside byte 0.
- With M5 the dead-to-silent ratio at 16 MHz (39 : 7 in B2, with 89 / 1
  six times as common as 89 / 2) says the dummy-byte start is the usual
  one there, roughly 5 to 1. B5 measures it.
- No overrun in any cell (`ovr` +0 throughout).
- No stuck cell outside the predicted zone, and silent cells exist at S7,
  so neither of B3's falsifiers fired. H2c is not needed.

|---|---|---|---|---|---|
| before the first clock | at once | 88 / 89 | 198 | 5 | healthy |
| at the first clock edge | dummy byte | 89 / 89 | 18 | 4 | healthy after the `retry` reset |
| inside byte 0 | at once | 88 / 1 | 31 | 25 | silent; 1 byte: healthy |
| inside byte 0, or between 0 and 1 | dummy byte | 89 / 1 | 84 | 77 | dead; 1 byte: healthy |
| inside byte 1 | at once | 89 / 2 | 18 | 45 | dead; 1 byte: silent |
| inside byte 1, or between 1 and 2 | dummy byte | 1 / 2, 1 / 1 | 100 | 62 | recovers |
| byte 2 on | either | TX ≤ RX | 671 | 92 | recovers |

- **Same classes at the same phases at 0.6, 4 and 16 MHz.** The stuck
  zone is bytes 0 and 1 of the raced frame at every clock, so its width in
  time scales with the bit time: about 1 µs at 16 MHz.
- "At once" share inside a byte: 31 of 101 in byte 0 and 18 of 89 in
  byte 1 at 16 MHz (about a quarter); 25 of 77 and 45 of 91 at 4 MHz;
  about half at 0.6 MHz. That is why silent is the rarer outcome at
  libwallaby's clock.
- Stuck links whose counters couldn't be read (15 in all) are placed by
  reply offset and 1-byte result.
- 1-byte transfer: silent → healthy in 56 of 56; dead 89 / 1 → healthy;
  dead 89 / 2 → silent. As B2 already showed, the plan's "not dead" was
  wrong and the model says why.

## Conclusion

Against "What counts as the solution": the first branch applies. B2 and B3
did not falsify the model of the stuck states (H1 needed widening to a
third count pair, which B1 had predicted), B6 found no cell F1 doesn't
leave, and B7 is clean.

- **A10 is the reset racing the first two bytes of a host frame.** It
  costs one extra reset with F1 and the link without it.
- **F1 (`4a731ea`) is sufficient.** F2 and F3 were not built. F2 would
  close the residual in B6 if that is wanted; nothing measured calls for
  it.
- **Why the stuck rate differed between images** (out of scope unless B3
  explained it): the zone is about 1 µs wide at a fixed place in each
  frame, so the rate is set by how the main loop's reset instant falls
  against the host's frame starts. That depends on loop timing, which the
  diag counters change. Not tested further.
- **Not established:** what makes the slave start at once or after a
  dummy byte (M5), and the chip-select hold after the last clock at
  16 MHz. Both need a logic analyzer or a marker pin to settle cheaply.

## Possible future work (left alone on the user's instruction, 2026-10-13)

- **Chip-select hold at 16 MHz.** An S7 sweep over the end of the frame
  on `a10-inj` or `a10-f1+inj` (about 8,000–10,000 cycles after chip
  select falls) shows how long this Pi keeps chip select low after the
  last clock, and so whether B6's residual is reachable. One flash.
- **F2.** Have the idle check also require the TX count to be 88. It makes
  the H4-type state visible to the firmware whatever the host does. Test
  on the 89 / 89 and 87 / 89 cells first, then B6's grid, B7, and P1–P15
  plus H1–H8.
- **M5.** What picks the slave's start mode. A logic analyzer on SCK and
  chip select with a marker pin at `SPI_Cmd` would settle it.
